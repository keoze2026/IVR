Week 1 was foundations. The goal was not to place a call - it was to get the
repository, the data model and the compliance layer right, because those are the
parts that are expensive to change later. Specifically the consent and
suppression tables: the spec is correct that retrofitting them is painful, and
everything downstream keys off them.

Completed this week:

    environment (Postgres 16 + Redis 7) running.
  - Full data model for accounts, contacts, consent, and suppression/DNC,
    including the multi-tenant base class and the tenancy guard.
  - Contact ingestion pipeline (CSV -> normalise -> dedupe -> suppression join)
    working end to end against a 50k-row test file.
  - Suppression gate and calling-window resolver written and unit tested.

Not started yet (planned for weeks 2-3): the pacer, the dialer, webhook
ingestion, the IVR flow engine, telemetry, and the REST API beyond what was

Rough completion against the spec as a whole: I would call it 25-30%. The data

5. PROBLEMS FOUND IN THE SPEC
--------------------------------------------------------------------------------

  Flagging these because they are in the spec's own sample code and someone
  else may copy them.

  1. DNC unique constraint does not do what it says.
     Spec 4.4 puts a UniqueConstraint on (organization, phone_e164,
     scope_campaign). scope_campaign is nullable, and Postgres treats NULLs as
     distinct, so this permits unlimited duplicate organisation-wide DNC rows -
     which are exactly the rows that most need to be unique. Replaced with two
     partial constraints, one for the scoped case and one for the NULL case.
     Also switched the match column from phone_e164 to phone_hash, because
     spec 4.8 requires suppression to survive erasure and erasure nulls the
     plaintext.

  2. is_dialable() references fields that do not exist.
     Spec 5.4 uses campaign.requires_consent and campaign.consent_scope. Neither
     appears in the Campaign model in spec 4.6. I have added both. Flagging in
     case they were meant to live elsewhere.

  3. Ingest row counting is wrong on re-upload (fixed, described Thursday).

  4. Unguarded timezone lookup in the sample ingest code (fixed, described
     Wednesday).

  5. The specification document I was given is truncated.
     It cuts off partway through section 6.1, mid-JSON. Sections 6.2 through 14
     - IVR node types, the pacer implementation, webhook handling, AMD,
     telemetry, the REST spec, security, deployment and the risk register - are
     not in the copy I have. I have enough from the diagrams and the section
     headings to keep moving for another week, but I will need the full
     document before I build the flow engine, and I would rather not guess at
     the node types. Requested on Wednesday, not yet received.

6. DECISIONS TAKEN - PLEASE CONFIRM
--------------------------------------------------------------------------------

  These are my calls. All are reversible now and progressively less so later.

  a) Consent checks are NOT cached.
     The spec caches the suppression result for 300 seconds and the consent
     check sits behind the same cache. I have pulled consent out of the cache.
     It is one indexed lookup, and it is the single check with statutory
     damages attached to getting it wrong. A five-minute stale "yes" on a
     revoked consent is not a trade I want to make on someone else's behalf.
     Cost: one extra query per dial attempt.

  b) The pacer gets its own Celery queue.
     The spec lists four queues. If pacer ticks share the dispatch queue they
     end up queued behind calls to the carrier, which means the pacing decision
     is paced by carrier latency. Small change, seemed clearly right.

  c) No table of US state calling-hour rules will ship in the code.
     I can build the mechanism - it is done - but I am not going to embed a
     table of state-by-state calling restrictions that I compiled myself. If it
     is wrong it will read as authoritative and nobody will re-check it.
     Proposal: the mechanism defaults to the federal ceiling, and someone with
     legal sign-off populates the per-state rows as configuration. This needs a
     decision from whoever owns compliance, not from me.

  d) Phone-hash pepper is effectively permanent.
     Rotating it orphans every stored hash and therefore every suppression
     record, with no migration path for erased contacts. Whoever sets it in
     production should know that. Recommend it goes into a secret manager on
     day one and is documented as unrotatable.
